# Мелкая графика кодом: локальная LLM в параллельном потоке

Здесь живёт конвейер «локальная модель пишет код, который делает графику».
Он нужен, чтобы мелкие визуальные улучшения шли **параллельно** с работой
арт-модели над крупными вещами (B1, B4), а не ждали её.

## Что это и чего это не делает

- Это **не** генератор картинок и не текст-в-3D. Локальная LLM пишет код:
  `game/scripts/*.cs` (Godot 4, C#), `tools/blender_*.py` (модели), шейдеры,
  GDScript-проверки. Ассет появляется потому, что код его строит.
- Правила игры (`core/`) модель не трогает вообще: раннер физически не даёт
  писать вне `game/` и `tools/`.
- Числа, влияющие на игру (цены, урон, расход), — не её дело: только визуал.
  Бюджеты кадра проверяются замерами, а не обещаниями.

## Как устроен процесс

```
tools/llm_art/tasks/<slug>/task.md   задание (цель, файлы, референсы, проверки)
              │
              ▼
tools/llm_art/run.py  ──► Ollama (qwen2.5-coder:7b) ──► файлы в текущий worktree
              │                                              │
              │                                              ▼
              │                                     dotnet build / blender
              │                                              │
              │                                     Godot-проверка (--selftest…)
              │                                              │
              │                                        снимок (--shot-…)
              ▼                                              ▼
build/llm_art/<дата>-<slug>/   промпт, ответы, файлы, логи, снимки — всё для ревью
```

1. **Одна задача — одна ветка и один worktree** (`git worktree add build/worktrees/<имя> -b feat/llm-art-<slug>`),
   чтобы поток не мешал арт-модели и архитектору.
2. Раннер сам пишет `.uid` новым `game/scripts/*.cs` (правило проекта) и не трогает
   `core/`.
3. Приёмка — **по снимку и проверкам**, не по коду:
   - сборка без предупреждений (предупреждение = красный);
   - `--selftest`/`--check-*` из задания;
   - `--perf` на глаз архитектора, если фича трогает кадр;
   - снимок `--shot-drive` / `*_review.gd` для арт-директора.
4. Слияние — только после `tools/check.ps1` и «да» на картинку.

## Команды

```powershell
# 1. ветка и worktree под задачу
git worktree add build/worktrees/dust -b feat/llm-art-dust master

# 2. прогон задания (модель по умолчанию qwen2.5-coder:7b, 5 попыток)
cd build/worktrees/dust
python tools\llm_art\run.py dust-vfx

# только собрать промпт и посмотреть, что уйдёт модели
python tools\llm_art\run.py dust-vfx --dry-run

# модель на процессоре, чтобы не отбирать видеопамять у Godot
python tools\llm_art\run.py dust-vfx --num-gpu 0

# другая модель / больше попыток
python tools\llm_art\run.py dust-vfx --model qwen2.5-coder:14b --attempts 8
```

Раннер печатает номер попытки, ошибки сборки/проверки и пути к файлам прогона.
Итог — строка в `tools/llm_art/RESULTS.md` (её и смотрит архитектор).

## Как добавить задачу

1. `mkdir tools/llm_art/tasks/<slug>` и скопировать `task_template.md`.
2. Заполнить верхний блок (машиночитаемый) и текст задания:

```
---
slug: dust-vfx
writes: game/scripts/CarDust.cs
refs: game/scripts/RainFx.cs, game/scripts/Car.cs:120-175, docs/ART.md:1-40
build: dotnet build game\Krntija.Game.csproj -v q --nologo
check: --selftest
shot: --shot-drive --at=40 --shot-name=llm_dust
---
```

- `writes` — какие файлы модель должна вернуть (остальные её правки отбрасываются).
- `refs` — что показать модели из репозитория (`путь` или `путь:с-по`).
- `build` — команда сборки (пустая строка — не собирать, например для блендер-генератора).
- `check` — флаги Godot для проверки без окна.
- `shot` — флаги Godot для снимка с окном (необязательно).

3. Прогнать на пробной ветке, посмотреть снимок, поправить задание при
   необходимости (формулировка задания влияет на результат сильнее модели).

## Что отдавать, а что нет

| Можно | Нельзя |
|---|---|
| VFX: пыль, дым, брызги, искры | числа игры: цены, урон, расход, шансы |
| Варианты пропсов, растительность, декор | контракты B1/B4 (кузов, якоря, панели) |
| Шейдеры и процедурные материалы | физика машины: `Anchors`, `RestLength`, `WheelRadius` |
| Снимки-обзоры и чекеры арта | бюджеты кадра «на глаз» без `--perf` |

## Ограничения машины

GTX 1060 6 ГБ, 16 ГБ RAM. 7B Q4 на GPU — быстро и безболезненно, пока Godot
не запущен; на CPU (`--num-gpu 0`) — медленнее, зато можно рендерить рядом.
Ветка с готовым результатом всё равно проходит обычный `check.ps1` (2–3 мин).
