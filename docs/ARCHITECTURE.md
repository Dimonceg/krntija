# Архитектура Krntija — правила для всех

Этот документ читают **все модели перед любой задачей** (графика, фичи,
архитектура). Он короткий намеренно. Если правило мешает — не обходите его
молча, а напишите в отчёте пользователю, почему; архитектор поправит документ.

Связанные документы: `AGENTS.md` (git и ветки), `docs/DESIGN.md` (какую игру
делаем), `docs/HANDOFF.md` (команды, грабли), `docs/ART.md` (контракт на модели).

---

## 1. Слои

```
core/Krntija.Core      правила игры: числа, состояния, решения. Без Godot.
core/Krntija.Core.Tests тесты на каждое правило.
game/scripts           показ и ввод: сцена, физика, звук, UI. Правил не придумывает.
game/assets            модели, текстуры, звук (контракт — docs/ART.md).
tools                  сборка, проверки, генераторы моделей.
```

**Главное правило.** Если в коде есть *число, которое влияет на игру* (цена,
урон, расход, шанс, вес, награда, время), оно живёт в `core` и покрыто тестом.
Сцена спрашивает у ядра «можно ли?» и «что вышло?», а сама только рисует.

Почему: баланс правится без запуска игры; в коопе правила выполняет хост,
и они не должны зависеть от того, у кого какая сцена; баги ловятся тестом
за миллисекунды, а не в плейтесте.

Как выглядит правильно (пример — `WorldActions.TryRepairAtWorkbench`):

```csharp
// core: решение и его причина
public static ActionResult TryRepairAtWorkbench(GameSession session, out Part? repaired)

// game: только показ результата
switch (WorldActions.TryRepairAtWorkbench(_car.Session, out var part))
{
    case ActionResult.NotEnoughMoney: _hud.Toast($"Нужно {WorldActions.WorkbenchPrice:F0} €"); break;
    ...
}
```

Неправильно: `if (session.Wallet.Money < 25) ...; session.Wallet.TrySpend(25);` в `Main`.

**Генерация мира — тоже правило.** «Что и где стоит» решает ядро
(`core/Krntija.Core/WorldGen`, ADR 0002), сцена строит геометрию по плану.
Генераторы в `game/scripts` (`RoadsideMap`, `BackcountryMap`, `MapLife`)
переезжают в ядро в фазе 3; новых решений «что поставить» в них не добавлять.

**Валюта — доллары.** Символ и формат цены — в одном месте ядра
(`Money.Format(…)`); строки в сцене не пишут `$` или `€` руками.

## 2. Состояние

- **Всё, что игрок может изменить в мире, должно сохраняться.** Подобранный
  лут, открытые шлагбаумы, посещённые места, разобранные завалы — это
  состояние, а не декорация. Хранится в ядре (`GameSession` и то, что она
  держит), попадает в `SaveData`, имеет тест «сохранил → загрузил → то же».
- Объекты мира, чьё состояние сохраняется, получают **стабильный id**, который
  не зависит от порядка создания узлов в сцене: `"<что>:<источник>:<номер>"`,
  где номер — из генератора по сиду. Конструкторы id — в `WorldState`
  (`WorldState.Loot("house", 3)`), отметка — `MarkWorld(id)`, показ после
  загрузки — `SyncWorldState()` в `Main.WorldState.cs`. Новый источник лута —
  новое имя источника, а не продолжение чужой нумерации.
- Изменения `SaveData` — по правилам ADR 0002, п. 6: новая версия читает
  предыдущую через значения по умолчанию; на каждую версию — образец
  `core/Krntija.Core.Tests/Saves/save_vN.json` и тест на его загрузку;
  ломающий переход — только с записью в ADR и только до первой публичной сборки.
- Мир генерируется **детерминированно по сиду** (`Pcg32`). Никаких
  `GD.Randi()`/`Random` в генерации: иначе карта разная у игроков в коопе
  и после загрузки.

## 3. Сцена (`game/scripts`)

- `Main` — partial-класс по темам (`Main.World.cs`, `Main.Interactions.cs`, …,
  таблица в `HANDOFF.md`). Новую механику кладите в подходящий файл или
  заводите `Main.<Тема>.cs`. **В `Main.cs` новых методов не добавлять.**
- Файл больше ~600 строк — повод разделить. Больше 1000 — делить обязательно.
- Самостоятельная штука со своим циклом (`RoadEvents`, `Car`, `Hud`) — свой
  `Node`, а не ещё один флаг в `Main`.
- **`Main` — только сборка сцены и маршрутизация ввода.** Окна (`Hud`,
  `BackpackUi`, `MapUi`) сами читают сессию и показывают её состояние; `Main`
  их создаёт и передаёт, что открыть. Новых обращений к полям окон из правил
  не добавлять: ядро возвращает результат, сцена показывает его одним вызовом.
  Отдельный интерфейс вида (`IPlayerView`) заводим, когда появится вторая
  реализация (кооп), не раньше.
- Генераторы мира (`RoadsideMap`, `BackcountryMap`, `MapLife`, `WorldScatter`) —
  статические классы: «построй по сиду и верни данные». Взаимодействия они не
  регистрируют сами, а возвращают описания (`MapUse`), которые регистрирует `Main`.
- Строки для игрока пишутся в сцене; числа в них берутся из констант ядра
  (`$"{WorldActions.MotelPrice:F0} €"`), а не дублируются текстом.
- Имена по смыслу: никаких `Foo2`, `NewFoo`, `FooFinal`.

### Мир кусками и плавающее начало координат

- Содержимое куска мира — только дети его корня (`Chunk_{k}`), в локальных
  координатах. Корни двигает и удаляет `ChunkStreamer`.
- Всё, что `Main` держит про кусок (точки взаимодействия, лут, места), помечено
  номером куска и снимается в `OnChunkUnloading`. `--chunk-run` и
  `--chunk-places` проверяют, что ссылок на выгруженные куски не осталось.
- Сцена всегда рядом с нулём; настоящая позиция = позиция сцены + `WorldOrigin`.
  **Поле с позицией сцены в `Main` — добавить в `ShiftScene`** (`Main.Chunks.cs`),
  иначе после сдвига оно указывает не туда.
- Шейдер, который берёт шум от мировой позиции вершины (`MODEL_MATRIX * VERTEX`),
  объявляет `global uniform vec3 world_origin;` и прибавляет его. Иначе узор
  перескакивает при сдвиге.

### `Variant` и результаты физических запросов

- Поля результата `IntersectRay`/`IntersectShape` читать только через
  `PhysicsHit.Collider<T>()` и `PhysicsHit.Position()`. `hit["collider"]`
  создаёт `Variant` со ссылкой на объект; неосвобождённые `Variant` финализируются
  после остановки движка и роняют Godot при выходе (так и было: проверки падали
  с 0xC0000005 через раз).
- Проверка (`--check-*`, `--selftest*`) выходит через `QuitSoon(код)`, а не
  `GetTree().Quit()`: так узлы из очереди удаления и финализаторы успевают
  отработать, пока движок жив.
- Ресурс Godot в статическом поле (общий материал, меш, кеш моделей, шум) —
  только с освобождением в `StaticCaches.Release()` (метод `ReleaseCaches` своего
  класса). Иначе обёртку финализирует .NET после остановки движка — падение при
  выходе. Выход из игры и проверок идёт через `StaticCaches.Release()`.
- Не вызывать `GetScript()` в циклах по узлам. Узел «со скриптом» — это узел
  нашего C#-типа: `node.GetType().Assembly == typeof(Main).Assembly`.

## 4. Производительность (бюджет на GTX 1060 6 GB)

Замер: `godot --path game -- --perf` (окно, VSync выключен на время замера).
Опорные цифры на 2026-10-25 (после `StaticBatcher`): **~5 мс на кадр,
221 МБ видеопамяти, 2110 узлов, 555 вызовов отрисовки** (до слияния было
2866 узлов и 1021 вызов). Разброс `--perf` между запусками — до 15 %:
сравнивайте по 2–3 прогона. Разбор сцены по частям — `--check-scene`.

| Метрика | Бюджет | Что делать, если превысили |
|---|---|---|
| Время кадра в `--perf` | ≤ 8 мс в среднем | найти, что добавили, и упростить |
| Видеопамять | ≤ 2 ГБ | сжать текстуры, уменьшить разрешение, атлас |
| Постройка куска мира | ≤ 4 мс в кадр | очередь на несколько кадров |
| Вызовы отрисовки | ≤ 1500 | MultiMesh, слияние статичных мешей |
| Узлы в сцене | ≤ 5000 | не делать узел на каждый ящик |
| Треугольники на модель | см. `docs/ART.md` | LOD, упростить |

- Повторяющееся (деревья, столбы, камни, трава) — только `MultiMeshInstance3D`.
- Неподвижная геометрия после постройки мира сливается `StaticBatcher`
  (меш на пару «ячейка 64 м × материал»). Он сам пропускает узлы со скриптом
  и всё под ними. **То, что код потом удаляет, двигает или перекрашивает без
  скрипта, добавьте в группу `StaticBatcher.SkipGroup`** — иначе удалённый
  узел останется видимым в слитом меше. Материал, который меняется во время
  игры, передайте в `keepInstance` (как мокрую дорогу в `BatchStaticGeometry`).
  Сравнить без слияния: `--no-batch`.
- Материалы всё равно переиспользуйте: `new StandardMaterial3D` на каждый ящик
  — это лишняя память и время постройки, даже если слияние склеит их потом.
- Ничего тяжёлого в `_Process` каждый кадр: поиск по всем точкам, `GetNode`,
  аллокации списков. Дорогое — по таймеру (как миникарта, 4 раза в секунду).
- Мир, который игрок не видит, не должен стоить кадров (см. «Бесконечная
  дорога» в `DESIGN.md`: мир будет подгружаться кусками).
- Если фича меняет цифры больше чем на 10 % — напишите цифры «до/после»
  в описании коммита.

## 5. Ассеты

Контракт — `docs/ART.md`. Коротко: GLB, метры, +Y вверх, лицо по −Z, центр на
земле; модель подменяется через `ModelLibrary`/`PropFactory` без правок логики;
коллизия — простыми формами, а не по мешу. Новая модель проходит `--check-props`.

## 6. Проверки

**Перед каждым слиянием:**

```powershell
.\tools\check.ps1
```

Ждём `ВСЁ ЗЕЛЁНОЕ — можно сливать`. Красное — не сливать. Если красное не от
вашей задачи — не чините вслепую чужое, а напишите пользователю.

Красный `master` возможен только на стыке двух веток. Чинит тот, чьё слияние
было вторым, в той же сессии; не может — пишет пользователю, тот решает, кому
отдать.

- Новое правило в ядре → тест в `core/Krntija.Core.Tests`.
- Новая механика в сцене, которую можно проверить без рук → шаг в `--selftest`
  или своя проверка `--check-<что>` в `Main.Diagnostics.cs` + строка в `check.ps1`.
- В описании коммита «с тестами» — только если тесты действительно в коммите.

## 7. Файлы и кодировки

- Исходники `.cs`, `.md`, `.gd`, `.py` — UTF-8 **без** BOM.
- Скрипты `.ps1` с кириллицей — UTF-8 **с** BOM (Windows PowerShell 5.1 иначе
  читает их как ANSI и ломается).
- Не писать файлы через `Set-Content`/`Out-File` без `-Encoding` (см. HANDOFF).
- `.uid` коммитятся вместе со скриптом. `.import` с LF (`.gitattributes`).
- Скриншоты для документации — в `docs/screenshots/`, не больше одного-двух на
  задачу, и только если они что-то показывают.

## 8. Кто за что отвечает

| Роль | Делает | Не делает без согласования |
|---|---|---|
| Графика | модели, текстуры, свет, VFX, `docs/ART.md` | правила игры, числа |
| Фичи | механики: ядро + сцена + тесты | структуру проекта, бюджеты |
| Архитектура | структура, правила, производительность, ревью, этот документ | новые механики без запроса |

Архитектор смотрит `master` примерно раз в день. Найденное чинит сам или
пишет задачу; о каждом таком изменении сообщает пользователю.
